# Детекция ботов по событиям внутри суточного окна

Решение целиком в `solution.ipynb`: выполняется сверху вниз и создаёт `submission.csv`.

**Результат:** `Precision @ Recall >= 0.70` = **0.839** на скрытом тесте (константа — 0.094,
baseline из quickstart — 0.099). На валидации 0.827.

## Как запустить

```bash
python -m venv .venv && .venv\Scripts\activate      # Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt jupyter
jupyter notebook solution.ipynb                     # Kernel -> Restart Kernel and Run All Cells
```

`metric.py` из условия должен лежать рядом с ноутбуком, данные — в подпапке `data/`. Полный прогон
занимает около 30 минут: большая часть времени уходит на валидацию и на проверки гипотез, сама
финальная модель обучается за пару минут.

```
.
├── data/                # из архива с данными, в репозиторий не коммитится
│   ├── train.csv
│   ├── test.csv
│   └── events.csv.gz
├── metric.py            # официальная метрика из условия
├── solution.ipynb
├── submission.csv
├── requirements.txt
└── README.md
```

Python 3.12.3, версии библиотек — в `requirements.txt`. Внешние API и языковые модели не
используются. `random_state` зафиксирован, бутстрэп детерминирован; повторный прогон даёт побайтово
идентичный `submission.csv` — проверка md5 в предпоследней ячейке.

## Какие признаки использовал

Готовых признаков нет, всё собирается из событий внутри окна `[window_start_ts, window_end_ts)`.
Одиннадцать групп, 99 признаков. Общая идея: робот дёшево наращивает объём и дорого имитирует
нерегулярность, поэтому вес отдан не счётчикам, а форме распределения.

| группа | что внутри |
|---|---|
| типы событий | счётчики, доли, энтропия по типам |
| воронка | контакты, избранное, свайпы — в отношении к числу просмотров, а не в абсолютах |
| разнообразие | уникальные объявления, категории, локации, запросы, доля повторных просмотров |
| пагинация | глубина выдачи, доля последовательных переходов 1→2→3 внутри запроса |
| время | статистики интервалов, берстность `(σ−μ)/(σ+μ)`, доля самого частого интервала, суточный профиль |
| платформа и UA | UA разобран на ОС, версию и маркеры автоматизации; ротация UA; рассогласование UA и platform |
| курсор | заполненность координат, разброс, доля уникальных позиций |
| мета куки | возраст куки на начало окна |
| концентрация обхода | индекс Херфиндаля по категориям, локациям, запросам |
| пиковая интенсивность | максимум событий в минуту и в 5 минут, отношение пика к медиане |
| контекст по корпусу | популярность просмотренных объявлений, запросов и локаций; число куки на том же UA |

Наибольший вклад: разнообразие обхода, пиковая интенсивность и контекст по корпусу. Курсор работает
только в связке — сам по себе даёт 0.11, но без него полный набор падает с 0.74 до 0.54. Отсюда же
следует, что permutation importance на этих данных занижает важность коррелированных признаков, и
оценивать надо группами.

Пропуски не заполняются: они структурные (у события нет такого поля), а `HistGradientBoosting`
обрабатывает их нативно. Для `ptr_*` пропуск означает «курсора не было вовсе» — забить его нулём
значило бы слить с «курсор был и не двигался».

## Как валидировался

Тест лежит строго позже трейна, поэтому валидация временна́я: пять расширяющихся окон, обучение
всегда на всём, что раньше валидационного среза. Двух фолдов, с которых я начал, не хватило — на них
суммарно около 260 ботов, и разброс между конфигурациями сопоставим с шумом.

Практическое правило, выведенное по ходу: **разницу меньше 0.03 одиночная модель на пяти фолдах не
различает.** Либо снижать дисперсию бэггингом, либо делать сравнение парным (одни и те же модели,
разная свёртка), либо не делать вывод. Дважды пренебрёг этим и дважды ошибся.

Валидация систематически занижает тест примерно на 0.03: финальная модель учится на всех 11 тысячах
строк, а любой фолд — на меньшем.

## Модель

`HistGradientBoostingClassifier`, 24 модели на бутстрэп-выборках, свёртка — **медиана рангов**.

Метрика ранжирующая и шумная, значит проблема в дисперсии, а не в смещении. Усредняются ранги, а не
вероятности: шкалы моделей несопоставимы, важен только порядок. Медиана вместо среднего даёт ещё
около 0.02 и выигрывает на всех пяти фолдах — одна модель из бутстрэпа может засунуть куку в резко
нетипичное место рейтинга, среднее тянется за таким выбросом, медиана его игнорирует.

Средняя вероятность подмешивается микровесом 0.001, чтобы развязать одинаковые медианные ранги:
метрика режет группы равных `score` целиком.

## Что пробовал и отбросил

Около семидесяти гипотез, рабочими оказались пять.

* **Календарные признаки** (день недели, час начала окна). С ними одиночная модель выглядит лучше, а
  под бэггингом с медианой — хуже. Классический случай, когда кажущийся прирост оказывается шумом.
  Выброшены: они описывают нарезку данных, а не поведение.
* **Target encoding user-agent.** После схлопывания версий во всём корпусе меньше двух десятков
  различных агентов. Это не высококардинальная категория, ради которой TE и нужен, — модель и так
  достаёт этот фактор из признаков `ua_*`.
* **Отбор признаков по важности.** Топ-30 даёт 0.51, топ-45 — 0.55 против 0.58 на всех. Слабые
  поодиночке признаки работают в связке.
* **Сессии оказались вырожденными**: у всех куки ровно одна сессия, разрыв больше 30 минут внутри
  суток не встречается ни разу.
* Не дали прироста: квантили и скошенность интервалов, автокорреляция интервалов, энтропия
  округлённых интервалов, тренд темпа; временна́я концентрация (HHI по минутам и часам, доля событий
  в пиковой минуте, пачки быстрых событий, коэффициент Джини) — всё семейство легло в шум, потому
  что сигнал уже вытащен признаком `peak_to_med_1m`; энтропия переходов между типами событий;
  динамика курсора (скорость, ускорение, извилистость); текстовые свойства запросов; новизна и
  синхронность объявлений; сырой user_agent категорией; логарифмы объёмов (деревья инвариантны к
  монотонным преобразованиям); число дублей строк. Перебор гиперпараметров — семь конфигураций,
  разброс ±0.05, то есть шум.

Характерная ловушка: несколько групп по отдельности давали +0.02...+0.04, а все вместе оказывались
хуже исходного набора. Это диагностический признак того, что приросты лежали в шуме.

## Ограничения

**Контекст по корпусу натягивает ограничение задачи.** Признаки `cr_*` считаются по событиям всего
корпуса, включая более поздние относительно окна конкретной куки. Меток они не используют, и на
скрытом тесте прирост подтвердился полностью (0.726 → 0.835). Но если требование «признаки доступны
на момент `window_end_ts`» трактовать строго, эту группу надо убрать — решение без неё даёт 0.726.
Разбор в разделе 8 ноутбука.

**Дрейф во времени.** Метрика падает от ранних фолдов к поздним. Модель привязана к поведению
парсеров конкретного периода, и заметная часть признаков обходится случайными задержками и ротацией
user-agent. Решение требует регулярного переобучения.

**`captcha_shown` — не независимый сигнал,** а следствие срабатывания уже существующего антибота.
Признак оставлен, но опираться на него при оценке способности ловить новые источники автоматизации
нельзя.

**Потолок задачи.** Отрицательный класс — трафик, *отнесённый* к человеческому, положительный —
трафик *известных* сервисов. Метки получены эвристикой, значит часть ботов заведомо сидит в нулях, и
модель не разделит выборку лучше, чем разделена сама разметка.
