# Детекция ботов по событиям внутри суточного окна

Решение целиком в `solution.ipynb`: выполняется сверху вниз и создаёт `submission.csv`. Ноутбук сохранён с выводами ячеек, поэтому числа со ссылкой на раздел сверяются без запуска. Результаты на скрытом тесте помечены отдельно - они получены на платформе при отправке.

| версия | пять коротких окон, медиана рангов | три длинных фолда, одна модель |
|---|---|---|
| 99 поведенческих признаков | 0.827 (на скрытом тесте 0.839) | 0.805 |
| + 13 средних репутации объявлений, 112 | не замерялось | 0.845 |
| + накопительный LLR, итого 113 | не замерялось | 0.854 |

Результат на скрытом тесте есть только для версии на 99 признаках: к моменту работы над репутацией лидерборд был закрыт. Прирост от репутации измерен на валидации, и ниже разобрано, почему две схемы оценивают его по-разному. Колонки отличаются не только фолдами, но и свёрткой: у коротких окон это медиана рангов восьми бутстрэп-моделей (раздел 10), у длинных фолдов - одна модель (разделы 11.3 и 11.6).

## Как запустить

```bash
python -m venv .venv
.venv\Scripts\activate                              # Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt jupyter
jupyter notebook solution.ipynb                     # Kernel -> Restart Kernel and Run All Cells
```

`metric.py` из условия должен лежать рядом с ноутбуком, данные - в подпапке `data/`. Полный прогон занимает около получаса, из них финальная модель - две минуты. Внешних API и языковых моделей нет. `random_state` зафиксирован, повторный прогон даёт побайтово идентичный `submission.csv`, md5-проверка стоит в последней кодовой ячейке.

Версии библиотек тут важны, а не формальность. Выводы получены на Python 3.13.15, numpy 2.4.4, pandas 3.0.2 и scikit-learn 1.8.0. На scikit-learn 1.9.1 те же признаки на фолде 13 апреля дают 0.786 вместо 0.820 у базы. Это та же ступенчатость метрики, что разобрана в разделе «Сколько стоит одно число на фолде»: смена версии слегка сдвигает модель, и куки у порога меняются местами. Поэтому в `requirements.txt` версии зафиксированы через `==`.

## Какие признаки использовал

Готовых признаков нет, всё собирается из событий. Двенадцать групп, 113 признаков.

### Поведение внутри окна, 99 признаков

Общая идея: робот дёшево наращивает объём и дорого имитирует нерегулярность, поэтому вес отдан не счётчикам, а форме распределения.

| группа | что внутри | P@R0.7 нарастающим итогом |
|---|---|---|
| типы событий | счётчики, доли, энтропия по типам | 0.154 |
| воронка | контакты, избранное, свайпы - в отношении к числу просмотров, а не в абсолютах | 0.156 |
| разнообразие | уникальные объявления, категории, локации, запросы, доля повторных просмотров | 0.214 |
| пагинация | глубина выдачи, доля последовательных переходов 1→2→3 внутри запроса | 0.263 |
| время | статистики интервалов, берстность `(σ−μ)/(σ+μ)`, доля самого частого интервала, суточный профиль | 0.318 |
| платформа и UA | UA разобран на ОС, версию и маркеры автоматизации; ротация UA; рассогласование UA и platform | 0.341 |
| курсор | заполненность координат, разброс, доля уникальных позиций | 0.492 |
| мета куки | возраст куки на начало окна | 0.540 |
| концентрация обхода | индекс Херфиндаля по категориям, локациям, запросам | 0.584 |
| пиковая интенсивность | максимум событий в минуту и в 5 минут, отношение пика к медиане | 0.650 |
| контекст по корпусу | популярность просмотренных объявлений, запросов и локаций; число куки на том же UA | 0.760 |

Таблица - одна модель на пяти коротких окнах (раздел 7). Самые крупные приросты при последовательном добавлении дают курсор (+0.151), контекст по корпусу (+0.110) и пиковая интенсивность (+0.067). Курсор при этом работает только в связке: сам по себе он даёт 0.113, но без него полный набор падает с 0.760 до 0.670. Значит, это не признак-читер, а взаимодействие - разброс координат разделяет куки только вместе с профилем активности. Отсюда же следует, что permutation importance здесь занижает важность коррелированных признаков, и считать надо группами.

### Репутация объявлений, 14 признаков

Единственная группа, использующая разметку других куки, и самый большой одиночный прирост за всю задачу. Задача про парсеров: сервис обходит не случайные объявления, а ограниченный каталог. Если объявление вчера смотрели известные боты, то кука, зашедшая на него сегодня, подозрительна независимо от того, как она ведёт себя внутри окна.

Формально это target encoding по `item_id`, свёрнутый с уровня объявлений на уровень куки: сглаженная доля ботов среди посетителей, её максимум и верхний квартиль, доли «горячих» (видел хоть один бот), «чистых» (видели только боты) и «холодных» (видели только люди) объявлений, покрытие, логарифм отношения правдоподобий, ставка со взвешиванием по редкости, средняя популярность.

Сглаживание `(b + α·p₀) / (n + α)`: при α = 5 объявление с единственным посетителем-ботом получает не 1.0, а 0.23. Взвешивание по редкости добавляет вес информативности - объявление, которое видели двое и оба боты, информативнее того, которое видели пятьсот человек и сорок ботов.

Разделение прямое: у ботов 44-54% их объявлений уже попадались известным ботам в прошлые дни, у людей 8-10% (раздел 11.1). Сам по себе признак слабый, AUC одного признака 0.77-0.83, но в связке с поведенческими даёт +0.04 на трёх длинных фолдах (раздел 11.3).

Четырнадцатый признак - накопительный LLR по «очищенному» пулу. Пул строится только из ботов, которые ходят по общему с другими ботами каталогу: не меньше 30% их объявлений видел ещё хоть один бот. Для куки с `k` объявлениями, `m` из которых попали в пул:

$$\mathrm{LLR} = m\log\frac{p_b}{p_h} + (k-m)\log\frac{1-p_b}{1-p_h},$$

где `p_b` и `p_h` - доли попаданий у ботов и у людей на истории. Это наивный Байес: попадания считаются независимыми испытаниями, свидетельства складываются, промахи штрафуют.

Чем это отличается от тринадцати средних, видно, если переписать формулу через долю попаданий `s = m / k`:

$$\mathrm{LLR} = k\,c\,(s - s^*), \qquad c = \log\frac{p_b(1-p_h)}{p_h(1-p_b)}, \qquad s^* = \frac{1}{c}\log\frac{1-p_h}{1-p_b}.$$

Средние измеряют интенсивную величину - долю `s`. LLR измеряет экстенсивную: ту же долю, отсчитанную от порога `s*` и умноженную на объём `k`, примерно как теплота отличается от температуры. На пуле финальной модели `p_b ≈ 0.65`, `p_h ≈ 0.05`, откуда `c ≈ 3.6` и `s* ≈ 0.27` (эти константы в ноутбуке не печатаются). Кука с двумя попаданиями из трёх получает LLR ≈ +4, кука с сорока из шестидесяти ≈ +86, хотя доли у них одинаковые.

Пропуски не заполняются, они структурные. Для `ptr_*` пропуск означает «курсора не было вовсе», забить его нулём значило бы слить с «курсор был и не двигался». Для репутации пропуск означает «ни одно объявление куки не встречалось в размеченной истории».

### Где у репутации сидит вторая утечка

Очевидную видно сразу: своя метка не должна попасть в свой признак. Менее очевидная и более дорогая - несовпадение зрелости пула между обучением и инференсом.

На тесте пул известен целиком, все четырнадцать размеченных дней лежат в прошлом относительно любого тестового окна. А для обучающей строки «прошлое» - это только дни до неё: у куки 6 апреля пула нет вовсе, у куки 7 апреля он в один день. Покрытие на обучении выходит 0.31 против 0.62 на инференсе, то есть модель учится на полупустом признаке и применяет выученное к насыщенному.

Решение - для обучающей строки брать все размеченные дни, кроме её собственного. Своя метка по-прежнему исключена, именно она и была бы утечкой, а покрытие на обучении поднимается до 0.56. Законность опирается на отдельный замер: сигнал не затухает, AUC одного признака держится на 0.77-0.83 при разрыве от 0 до 6 дней без тренда (раздел 11.1), парсеры возвращаются к одному каталогу изо дня в день. Раз направление сдвига во времени не важно, пул «вокруг» статистически эквивалентен пулу «до».

Цена вопроса - 0.030 на фолде: 0.827 у варианта «только прошлое» против 0.857 (раздел 11.2). Обе версии есть в коде. Если трактовать требование «признаки доступны на момент `window_end_ts`» максимально строго, так что и обучающая выборка не вправе смотреть вперёд, надо брать осторожную.

Обобщение: когда признак зависит от объёма накопленной истории, разница в этом объёме между обучением и инференсом сама становится источником ошибки, и лечится она выравниванием, а не регуляризацией.

Но у правила есть граница, и накопительный LLR в неё упирается. В конструкции «все дни, кроме своего» он на двух фолдах выигрывает, а на третьем теряет 0.026; в конструкции «только прошлое» не проигрывает нигде (раздел 11.6). Причина видна из формулы выше: LLR пропорционален `k`, и систематическое расхождение в частоте попаданий между обучающим и инференсным пулом, ничтожное на одно объявление, тоже умножается на `k`. Сигнал интегрируется вместе со смещением. Отсюда уточнение: чем сильнее статистика накапливает свидетельства, тем точнее её обучающая конструкция должна повторять инференсную. Средним можно выравнивать зрелость пула, суммам нельзя, поэтому LLR считается строго по прошлому.

## Как валидировался

Тест лежит строго позже трейна, поэтому валидация временна́я. Схем две:

- пять расширяющихся двухдневных окон (раздел 4) - для поведенческих признаков;
- три длинных фолда с границей 13, 15 и 17 апреля (раздел 11.3) - для репутации. У фолда 13 апреля 408 ботов против примерно 120 у двухдневного, и только при таком объёме разница в 0.03 перестаёт тонуть в шуме.

На репутации прямого сравнения схем нет: короткие окна с ней в сохранённом прогоне не замерялись. Сравнивать схемы на базовом наборе надо при одинаковой свёртке. У одной модели короткие окна дают 0.760, длинные фолды - 0.805 (разделы 7 и 11.3). У медианы рангов - 0.827 и 0.801 (разделы 10 и 11.3). Схемы меняются местами в зависимости от свёртки, и ни одна не завышает систематически.

У каждой свой дефект. Короткие окна - это десятки ботов на фолд, и одна кука через порог стоит до 0.01. Длинные фолды обучаются на половине данных: 5 930 строк против 11 091 в финале. Правдоподобная гипотеза: репутация частично замещает объём обучающей выборки, на половине данных поведенческая модель недоучена и внешняя подсказка весит больше. Если так, прирост в финале меньше замеренных +0.04. Проверить это нельзя: фолда, у которого одновременно сотни ботов в валидации и полный обучающий набор, четырнадцать дней данных не дают. Связь с лидербордом известна только для коротких окон, 0.827 там дали 0.839 на тесте.

### Сколько стоит одно число на фолде

Самое полезное, что я понял за задачу. Я переписал код репутации аккуратнее и поменял базовую долю с округлённой `p₀ = 0.0810` на `p₀ = ȳ = 0.081057`. Это константа сглаживания, её третий знак не несёт смысла, признаки сдвигаются на 5·10⁻⁵. А метрика на фолде поехала с 0.885 на 0.864 (раздел 11.4).

Обычная проверка устойчивости этого не ловит. `HistGradientBoostingClassifier` здесь от `random_state` не зависит: случайность в нём используется только для отложенной выборки ранней остановки и для `max_features < 1`, а оба механизма выключены. Разброса по seed нет вообще, и замер выглядит точным.

Причина в геометрии метрики. `P@R` при фиксированном recall кусочно-постоянна на порядке куки, значение меняется только когда кука переходит через порог. На фолде 13 апреля порог отсекает около 340 куки, так что перестановка девяти из них - уже 0.02. Поверхность не гладкая, а ступенчатая, и малые сдвиги перебрасывают модель между ступеньками, а не двигают её вдоль градиента.

Поэтому разброс надо мерить, варьируя то, что произвольно по смыслу - `p₀` и силу сглаживания `α`, - а не случайность модели. По пяти одинаково законным комбинациям (раздел 11.4):

| вариант | медиана | разброс |
|---|---|---|
| одна модель | 0.877 | 0.021 |
| бэггинг, медиана рангов | 0.857 | 0.003 |
| бэггинг, среднее рангов | 0.865 | 0.010 |
| смесь 0.7 / 0.3 | 0.888 | 0.022 |

Узкий разброс медианы рангов - не достоинство: она стабильно держится около 0.857, то есть стабильно ниже остальных. Решающее сравнение здесь парное, при одних и тех же константах. Смесь выигрывает у одиночной модели в четырёх строках из пяти, а её худшее значение (0.875) выше лучшего у обоих вариантов бэггинга (0.859 и 0.872).

Правило «разницу меньше 0.03 одиночная модель не различает» этим подтверждается, но причина не та, которую я в него вкладывал изначально. Я думал про дисперсию по обучающей выборке. Основной вклад даёт чувствительность к произвольным мелочам конструкции признака, и она невидима, если менять только seed и фолды. Смена версии scikit-learn сдвигает числа на ту же величину, это то же самое явление.

## Модель

`HistGradientBoostingClassifier` на 113 признаках. Итоговый score - смесь нормированных рангов: 0.7 на модель, обученную на всех данных, и 0.3 на среднее рангов 24 моделей на бутстрэп-выборках.

Метрика ранжирующая и шумная, значит проблема в дисперсии, а не в смещении. Усредняются ранги, а не вероятности: шкалы моделей несопоставимы, важен только порядок. Средняя вероятность подмешивается микровесом 0.001, чтобы развязать одинаковые ранги, метрика режет группы равных `score` целиком. В сабмите все 4 909 значений уникальны (раздел 12).

Правка к прошлой версии. Раньше здесь стояла чистая медиана рангов 24 бутстрэп-моделей и утверждение, что медиана даёт около +0.02 против среднего (0.827 против 0.809 на коротких окнах, раздел 10). На длинных фолдах это не воспроизводится: на базовом наборе фолда 13 апреля медиана даёт 0.797 против 0.834 у среднего, а в среднем по трём фолдам с репутацией - 0.851 против 0.855 (раздел 11.3). Промежуточный вывод «с сильными признаками бэггинг больше не нужен, одиночная модель лучше» тоже оказался артефактом: 0.885 у одиночной модели - удачное попадание в ступеньку.

Выбор смеси опирается на парное сравнение из таблицы выше. На трёх длинных фолдах смесь и среднее рангов практически равны (0.854 и 0.855), обе выше одиночной модели (0.845) и медианы (0.851). Содержательно бутстрэп сглаживает ступенчатость, но теряет около 37% уникальных строк в каждой модели, а ботов всего 899. Поэтому полезны оба слагаемых, а не одно.

Финальная свёртка на 113 признаках отдельно на валидации не замерялась: в разделах 11.3 и 11.4 - 112 признаков, в 11.6 - одна модель.

## Что пробовал и отбросил

Вокруг репутации (раздел 11.5, фолд 13 апреля, одна модель, база с репутацией объявлений 0.857):

- Репутация поисковых запросов - 0.854, то есть ноль. Её бот-ставка это уже известная модели информация, перепакованная в новые колонки.
- Очищенный пул как набор средних - 0.868, то есть +0.011. Это внутри разброса 0.021 из таблицы выше, а признаков становится вдвое больше. Сигнал очищенного пула целиком забирает один накопительный LLR (раздел 11.6).
- Накопительный LLR в конструкции «все дни, кроме своего» - на фолде 17 апреля −0.026, причина разобрана выше: сумма интегрирует смещение пула вместе с сигналом.

Вокруг поведения:

- Календарные признаки (день недели, час начала окна). Одиночная модель 0.760 → 0.779, то есть как будто плюс; под бэггингом с медианой 0.827 → 0.814, то есть минус (раздел 10). Выброшены: они описывают нарезку данных, а не поведение.
- Target encoding user-agent, 0.760 → 0.768 (раздел 9). После схлопывания версий во всём корпусе 19 различных агентов. Это не высококардинальная категория, ради которой TE и нужен, а прирост меньше порога различимости.
- Отбор признаков по важности прироста не дал: топ-30 - 0.758, топ-45 - 0.743 против 0.760 на всех 99 (раздел 9). Все три значения внутри порога различимости, а немонотонность (топ-30 выше топ-45) сама по себе признак шума. Обрезать набор незачем, слабые поодиночке признаки работают в связке.
- Сессии оказались вырожденными: у всех куки ровно одна сессия, разрыв больше 30 минут внутри суток не встречается ни разу (раздел 9).
- Не дали прироста (замеры из ранней версии ноутбука, код этих проверок в текущую не вошёл): квантили и скошенность интервалов, автокорреляция интервалов, энтропия округлённых интервалов, тренд темпа; временна́я концентрация (HHI по минутам и часам, доля событий в пиковой минуте, пачки быстрых событий, коэффициент Джини) - сигнал уже вытащен признаком `peak_to_med_1m`; энтропия переходов между типами событий; доля просмотров без предшествующего поиска; динамика курсора; текстовые свойства запросов; новизна и синхронность объявлений; сырой user_agent категорией; логарифмы объёмов (деревья инвариантны к монотонным преобразованиям); число дублей строк; перебор гиперпараметров по семи конфигурациям.

Характерная ловушка: несколько групп по отдельности давали +0.02...+0.04, а все вместе оказывались хуже исходного набора. Это диагностический признак того, что приросты лежали в шуме.

## Открытый вопрос

Репутация по сырому user-agent. В сохранённом замере (раздел 11.5) она даёт 0.887 против 0.857, больше любой другой проверенной добавки. В итоговые 113 признаков группа не вошла: по структуре это та же информация, что уже вытащена группой `ua_*` и счётчиком кук на том же агенте, а +0.030 на одном фолде лишь в полтора раза больше разброса из таблицы выше. Но единственный замер этого не доказывает. Чтобы решить, нужен прогон на трёх фолдах с вариацией констант сглаживания и парным сравнением - ровно та процедура, которую требует раздел 11.4. До этого прогона вопрос открыт: число в таблице не основание включать признак, но и не основание его отбрасывать.

## Ограничения

Репутация и контекст по корпусу натягивают ограничение задачи, но по-разному. Признаки `cr_*` считаются по событиям всего корпуса, включая более поздние относительно окна конкретной куки. Меток они не используют, и на скрытом тесте прирост подтвердился полностью, 0.726 → 0.835 (раздел 8). Репутация использует метки, но на инференсе причинна: для тестовых строк пул целиком лежит в прошлом. Вперёд смотрит только построение обучающих строк для тринадцати средних, и обоснование этому - отсутствие затухания сигнала. Осторожные варианты обеих групп есть в коде: без `cr_*` решение дало на скрытом тесте 0.726, с пулом «только прошлое» вместо «все дни, кроме своего» - 0.827 против 0.857 на фолде.

Дрейф во времени. Модель привязана к поведению парсеров конкретного периода, и заметная часть поведенческих признаков обходится случайными задержками и ротацией user-agent. Решение требует регулярного переобучения. Репутация объявлений от ротации UA, наоборот, не страдает, и это аргумент в её пользу помимо метрики.

Репутация требует инфраструктуры. Поведенческие признаки считаются по одной куке. Репутации нужна актуальная таблица «объявление - сколько размеченных куки и ботов среди них» с обновлением по мере поступления новых меток. В продакшене это не признак, а отдельный сервис.

`captcha_shown` - не независимый сигнал, а следствие срабатывания уже существующего антибота. Признак оставлен, но опираться на него при оценке способности ловить новые источники автоматизации нельзя.

Потолок задачи. Отрицательный класс - трафик, отнесённый к человеческому, положительный - трафик известных сервисов. Метки получены эвристикой, значит часть ботов заведомо сидит в нулях, и модель не разделит выборку лучше, чем разделена сама разметка. Репутация этот потолок не поднимает, а упирается в него прямее остальных признаков: она переносит на новую куку то, что уже известно о старых, и вместе с этим систематические ошибки разметки.
